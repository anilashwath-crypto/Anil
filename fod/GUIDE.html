Field Manual

Everything needed to understand and commission FOD Guard — the CCTV pre-cycle inspection gate in fod/index.html. It explains what the system does and how the detection actually works, then walks through hardware, wiring, software, job setup, tuning, multi-machine (central) deployment, and troubleshooting.

01What the system does

FOD Guard turns one fixed CCTV camera pointed at a machine's die/fixture into a pre-cycle inspection gate. The operating contract is simple:

  1. Teach once per job. With the part loaded correctly, capture one master image and drag a box marking the inspection zone (the die area). Everything outside that box — hands, walkways, the operator — is ignored forever.
  2. Check every cycle. Each time the job is reloaded, the app grabs a frame and answers two questions inside the zone: is the part present and sitting the right way round? and is anything in the zone that wasn't in the master?
  3. Gate the door. Only when both answers are good does it call the Lock URL — an HTTP relay wired to the door solenoid — so the door locks and the cycle is enabled. Any fault calls the Unlock/inhibit URL, shows a red banner, beeps, and names the reason (misoriented, wrong/missing part, or foreign objects with red boxes drawn on the snapshot).

Every check is logged with a timestamp, verdict, score, and annotated thumbnail. All data (jobs, settings, history) lives in the browser's localStorage and can be exported/imported as one JSON file. The UI is trilingual (English / ಕನ್ನಡ / हिंदी) with a day/night toggle. To see the whole decision play out on a simulated machine before touching hardware, open fod/explainer.html.

02How detection works, in depth

Everything runs in the browser on plain pixels — no cloud, no training, no neural network. That's a deliberate choice: it is explainable, deterministic, and runs on a Raspberry Pi. Five stages per check:

2.1 Capture & reduce

A frame is grabbed at 640 px wide. The inspection-zone rectangle is cut out, scaled down to at most 144 px on its longer side, converted to grayscale, and blurred (two 3×3 box passes). The blur is not laziness — it makes the comparison tolerant of sensor grain and sub-pixel wobble so that only real changes survive to later stages.

2.2 Find the part: pose search

The live zone image is compared against the master zone image at many candidate poses: rotations −12°…+15° in 3° steps plus the flipped positions 90°, 180°, 270°, each combined with pixel shifts up to ±8 px. Every pose gets a score — the normalized cross-correlation (Pearson correlation of the two images' pixels), which is 1.0 for a perfect match, ~0 for unrelated content, and is immune to overall brightness changes. The best coarse pose is then refined in 1° / 1 px steps and finally in 0.5° / 0.5 px steps, so residual misalignment is tiny.

The best pose and its score decide the orientation verdict:

Result of the searchVerdict
Best score ≥ threshold, best angle within ±6°ORIENTATION OK — a part that merely sits a little off still passes; the found shift/angle is remembered for stage 2.3
Best score ≥ threshold, but at a bigger angle (e.g. 15°, 180°)MISORIENTED ~N° — the part is there, the wrong way round
No pose reaches the thresholdJOB MISSING / WRONG JOB — empty fixture, or a different part that doesn't correlate with this job's master

2.3 Foreign objects: aligned difference

Only when orientation is OK does the foreign-object stage run. The live image is resampled through the found pose so it lies exactly on top of the master, both images are normalized to the same mean and contrast (this cancels lighting drift between shifts, seasons, or a dimming lamp), and subtracted pixel by pixel. What remains is only what changed since the master was taught.

Pixels whose difference exceeds the sensitivity threshold are marked, and connected patches are grouped into blobs. Any blob larger than the minimum object size (a percentage of the zone) is a foreign object — a forgotten nut, a spanner, a chip of scrap — and is boxed in red on the snapshot. Grain, glare speckle, and tiny edge ghosts fall below the size floor and are ignored.

2.4 The decision gate

The verdict is a strict AND — the door is never locked on a hunch:

orientation OK  AND  zero foreign objects   →  ALL CLEAR  →  GET/POST Lock URL    →  door locks, cycle enabled
anything else                                →  FAULT      →  GET/POST Unlock URL  →  cycle inhibited, red banner + beep

2.5 Record

The annotated snapshot, verdict, score, angle and foreign-object count are pushed to the cycle log (latest 60 kept), which persists across restarts.

Why this design is robust on a real floor
Each cycle the part lands a few millimetres off and lighting drifts — the pose search and normalization absorb exactly those two nuisances, so thresholds can stay tight enough to catch a single nut without crying wolf every cycle.

03Hardware & wiring

Complete priced list: fod/BOM.md / fod/FOD_Guard_BOM.xlsx (₹22,275 per standalone machine incl. contingency; central multi-machine variant in section 09). What matters for a reliable install:

3.1 Camera — three ways in

You haveConnect it asApp setting
USB webcamStraight into the computerSettings → Source → Device / USB camera
Analogue / HDMI CCTV or DVR spot outputUSB capture dongle into the computerSame — the dongle appears as a camera
IP camera / NVR channelOver the LANSettings → Source → IP camera snapshot URL — a JPEG endpoint such as /snapshot.jpg or /cgi-bin/snapshot.cgi

Mounting rules that matter more than resolution: bolt the camera to something that does not vibrate (the machine frame with a rubber isolator, or a wall bracket), aim it so the die fills a good share of the frame, and never let it be nudged — the master is only valid for one exact viewpoint. 2 MP is plenty; a rock-steady 2 MP image beats a shaky 4K one every time.

3.2 Lighting — the single biggest reliability lever

Mount a small LED floodlight (≈20 W, neutral white) so the zone is lit the same at 7 am and 7 pm, with a hood so the lamp never shines into the lens. Consistent light does more for detection quality than any threshold tuning. If reflections off polished parts cause trouble, angle the lamp across the die rather than down onto it.

3.3 Lock, relay and indication

  • Relay node: either a Shelly 1 (ready-made, has an HTTP API out of the box) or an ESP32 + 2-channel opto relay (sketch in section 05). Powered from the 12 V rail through a 12→5 V buck.
  • Lock: a 12 V DC solenoid bolt (spring-return) on the guard door, or a 180 kg electromagnetic lock for flush door faces. Fit a flyback diode across the coil (1N5408, striped end to +12 V) — without it the relay contacts pit and fail within weeks.
  • Tower light (recommended): relay channel 2 mirrors the verdict so the operator sees red/green at the machine without looking at the screen.
  • Everything low-voltage lives in one IP65 box on DIN rail next to the door, mains via an MCB.

3.4 Computer

Anything that runs a modern browser: a Raspberry Pi 4 in Chromium kiosk mode with a 7" touchscreen at the machine, a spare Windows/Linux PC, or an Android tablet. For the Pi, autostart the kiosk with:

chromium-browser --kiosk --noerrdialogs --disable-restore-session-state \
  http://localhost:8000/fod/index.html

04Software setup

4.1 Serve the app

The app is one file with no build step. Serve the repo folder and open it:

cd Anil
python3 -m http.server 8000
# open  http://localhost:8000/fod/index.html

Three hosting rules decide what works where:

Page served fromLocal camera (getUserMedia)IP camera / relay over http://
http://localhost:8000✔ works (localhost counts as secure)✔ works
http://<LAN-IP>:8000 (another device on the LAN)✘ blocked by browsers✔ works — use IP-camera mode
https://…github.io/… (GitHub Pages)✔ works✘ blocked — an https page may not call http URLs (mixed content)
Rule of thumb
USB/webcam at the machine → localhost or GitHub Pages, either is fine. IP cameras and HTTP relays → serve over plain http:// from the supervising computer (localhost) so the browser is allowed to call the camera and relay URLs.

4.2 Configure Settings (⚙ tab)

  1. Camera source — Device / USB camera (then pick the camera from the list after starting it once) or IP camera snapshot URL. The snapshot endpoint must return a JPEG and allow cross-origin requests (CORS); most CP Plus / Hikvision / Dahua cameras and DVRs expose one — check the model's manual for /snapshot.jpg, /cgi-bin/snapshot.cgi or ONVIF snapshot URI. If the camera refuses CORS, run the tiny proxy from section 09.3 on the supervising PC.
  2. Door-lock relay — paste the Lock URL and the Unlock/inhibit URL, pick GET or POST, and use Test lock/Test unlock: you should hear the relay click and see the bolt move. Leave the URLs blank to run with the on-screen indicator only (useful during commissioning).
  3. Backup — after commissioning, Export the JSON once and keep it; it restores every job, master, threshold and URL onto a replacement device in one step.

5.2 DIY ESP32 sketch

Complete sketch for the ESP32 + 2-channel relay in the BOM — flash from the Arduino IDE, set your Wi-Fi credentials, note the IP it prints:

#include <WiFi.h>
#include <WebServer.h>

const char* SSID = "PLANT-WIFI";
const char* PASS = "********";
const int LOCK_PIN  = 26;   // relay CH1 — door solenoid
const int LIGHT_PIN = 27;   // relay CH2 — tower light (green when locked)

WebServer server(80);

void setPins(bool locked){
  digitalWrite(LOCK_PIN,  locked ? HIGH : LOW);
  digitalWrite(LIGHT_PIN, locked ? HIGH : LOW);
}

void handle(bool locked){
  setPins(locked);
  server.send(200, "text/plain", locked ? "LOCKED" : "UNLOCKED");
}

void setup(){
  pinMode(LOCK_PIN, OUTPUT); pinMode(LIGHT_PIN, OUTPUT);
  setPins(false);                          // boot UNLOCKED — the safe default
  WiFi.begin(SSID, PASS);
  while (WiFi.status() != WL_CONNECTED) delay(300);
  Serial.begin(115200);
  Serial.println(WiFi.localIP());          // -> use in the app's URLs
  server.on("/lock",   [](){ handle(true);  });
  server.on("/unlock", [](){ handle(false); });
  server.begin();
}

void loop(){ server.handleClient(); }

App URLs become http://<esp32-ip>/lock and http://<esp32-ip>/unlock. The sketch boots unlocked — the safe default: a power cut never leaves the gate asserting "clear".

06Setting up the first job

  1. Prepare the scene. Floodlight on, die clean, the part loaded exactly as a good cycle should look.
  2. Monitor tab → Start camera (device mode) and confirm the live view shows the die sharp and well lit.
  3. Jobs tab → New job → name it after the part and operation (e.g. Flange 80mm — Op.20).
  4. Capture master from camera. The frozen frame appears below.
  5. Drag the inspection zone on the master — a tight box around the die and part. Tight matters twice: things outside can never cause a false alarm, and the minimum-object-size percentage refers to this box, so a tighter box detects smaller objects.
  6. Leave the three sliders at their defaults for now (60% / 45 / 0.5%).
  7. Save job. It appears in the Monitor tab's job selector.
  8. Prove it before trusting it — run this acceptance sequence:
    • Correct load → expect ALL CLEAR, relay clicks, bolt in.
    • Part rotated / flipped → expect MISORIENTED.
    • Part removed → expect JOB MISSING.
    • Smallest object you care about (a nut, an insert) laid in the zone → expect FOREIGN OBJECT with a red box on it.
    If any of the four misbehaves, go to section 07 — one slider fixes each symptom.
Re-teach when the world changes
Re-capture the master whenever tooling, the camera position, or the lighting rig changes. It costs 30 seconds; a stale master costs a shift of false alarms.

07Tuning the three thresholds

Slider (per job)DefaultWhat it meansRaise it when…Lower it when…
Orientation match required60% Minimum correlation score to accept that the right part is present A wrong-but-similar part from another job slips through as "misoriented" instead of "wrong job" Good loads are wrongly reported as "job missing" (dark scene, low-contrast part — fix lighting first)
Foreign-object sensitivity45 How different a pixel must be (gray levels) before it counts as changed. Lower number = more sensitive Glare/reflection patches get flagged as objects A low-contrast object (dark tool on dark plate) is missed
Minimum object size0.5% of zone Blobs smaller than this are ignored Speckle, dust or chips you don't care about trigger alarms The smallest object you must catch isn't flagged (also consider a tighter zone or closer camera)

Tune with the real acceptance sequence from 06 after every change — one slider at a time, and only after lighting and mounting are solid. Nine of ten false-alarm problems are light or vibration, not thresholds.

08Daily operation

  • Per cycle: reload the job, press ▶ RUN CYCLE CHECK (or the Space bar). Green banner → door locks → run the cycle. Red banner → the reason and any red boxes are on the snapshot; clear the cause, press Back to live, check again.
  • Auto mode: tick Auto every N sec to re-check on a timer — useful while dialling in, or as a continuous watch on a slow process.
  • Changeover: pick the new part's job in the selector — every job carries its own master and thresholds.
  • Log tab: last 60 checks with verdict and annotated thumbnail — the shift-end evidence trail for why a cycle was inhibited.
  • Weekly: wipe the lens, glance at the tower light bulbs, and export a JSON backup after any job change.

09Central mode: many machines, one computer

Past a couple of machines, drop the per-machine computer: one PC on the plant network supervises every cell. Each machine keeps only its camera (PoE), floodlight, and relay node; the PC runs the app for all of them. Priced in FOD_Guard_BOM.xlsx → Central tab — head-end ₹29,800 once + ₹10,150 per machine (4 machines ≈ ₹77,440 vs ₹89,100 standalone).

9.1 How the app models it

  • Create one job per machine (the part currently running on it) and fill the job's Central-mode fields: that machine's camera snapshot URL, and its own lock/unlock relay URLs. Blank fields fall back to the global Settings, so single-machine use is unchanged.
  • A job with its own snapshot URL needs no local camera — RUN CYCLE CHECK fetches the frame over the network.
  • 🏭 CHECK ALL MACHINES sweeps every job that has a camera URL, one after another: each machine's own relay is fired, every result is logged, and the final banner names exactly the machines that failed.
  • If one machine runs several parts, keep a job per part per machine (e.g. Press-02 · Flange 80) — pick the active one at changeover; CHECK ALL will sweep whatever jobs currently carry camera URLs.

9.2 Network layout

  • Cameras home-run over Cat6 to a PoE switch at the PC (the switch powers them).
  • Relay nodes join the plant Wi-Fi (ESP32/Shelly) — no extra cabling.
  • Give every camera and relay a DHCP reservation; label each with its IP.
  • Serve the app from the central PC over http://localhost:8000 (section 4.1's mixed-content rule: http page → http cameras/relays all allowed).

9.3 If a camera refuses CORS

Most CCTV cameras serve JPEG but without the CORS header the browser needs to read pixels — the live picture displays, yet capture/check fails. Run the proxy shipped as fod/snapshot_proxy.py (same code as below) on the supervising PC and use http://localhost:8090/?u=http://<cam>/snapshot.jpg as the camera URL:

from http.server import BaseHTTPRequestHandler, HTTPServer
from urllib.parse import urlparse, parse_qs
import urllib.request

class Snap(BaseHTTPRequestHandler):
    def do_GET(self):
        url = parse_qs(urlparse(self.path).query).get("u", [None])[0]
        if not url: self.send_error(400); return
        data = urllib.request.urlopen(url, timeout=5).read()
        self.send_response(200)
        self.send_header("Content-Type", "image/jpeg")
        self.send_header("Access-Control-Allow-Origin", "*")
        self.end_headers(); self.wfile.write(data)

HTTPServer(("127.0.0.1", 8090), Snap).serve_forever()

11Safety boundaries

⚠ Read before wiring
FOD Guard is a process-assist check — it protects the die and the part from crashes and forgotten objects. It is not a certified safety device and must never become one:
  • The machine's certified guard interlock (safety relay, guard switch, light curtain — per the machine's applicable safety standard) stays in place, on its own circuit. FOD Guard's lock is wired in addition to it, never instead of it.
  • Fail-safe direction: on power loss or network loss the relay de-energises and the gate reads "not clear" — the system can only withhold permission, never force a cycle.
  • Never let an "ALL CLEAR" screen substitute for the operator's own look into the die area.
